# ENKO — HVAC-каталог на WordPress

Кейс: міграція статичного HTML-прототипу у повноцінний сайт на **WordPress + WooCommerce**
у режимі каталогу («заявка» замість онлайн-оплати), з двомовністю, кабінетами користувача
й менеджера, двостороннім чатом у Telegram і власним шаром оптимізації та безпеки.

🔗 **Живий сайт:** [enkogroup.com.ua](https://enkogroup.com.ua)

## 🎯 Задача

Клієнт — постачальник кліматичної техніки (кондиціонери, VRF, теплові насоси, вентиляція,
фанкойли). Потрібен був не інтернет-магазин, а **каталог-вітрина з моделлю «заявка»**: відвідувач
збирає техніку в заявку, менеджер зв'язується і прораховує вартість із доставкою та монтажем
індивідуально. Плюс — робота з B2B-клієнтами (персональні знижки, закріплений менеджер, чат).

**Вихідна точка:** статичний HTML-прототип із власним дизайном (у теці `prototype/`).
**Результат:** WordPress-сайт, візуально ідентичний прототипу (1:1), із повноцінною бізнес-логікою.

## 🏗 Архітектура

Логіка свідомо розділена на два незалежні шари:

```
wordpress/
├── themes/enko/          ← класична тема: 1:1 порт дизайну прототипу
│   ├── *.php             ← шаблони сторінок + WooCommerce-оверрайди
│   ├── styles/           ← CSS прототипу (4 файли)
│   └── scripts/          ← JS прототипу (3 файли)
├── plugins/enko-core/    ← уся бізнес-логіка (25 модулів)
│   ├── inc/*.php
│   └── assets/*.js|css
└── dropins/              ← page-cache + серверні сніпети
```

**Чому так:** тема відповідає лише за вигляд, плагін — за поведінку. Зміна чи оновлення теми
не зачіпає бізнес-логіку; логіка не «прив'язана» до дизайну.

### Модулі плагіна (вибірково)

| Модуль | Відповідальність |
|---|---|
| `catalog-mode.php` | режим каталогу — прибирає оплату/кошик WooCommerce |
| `pricing.php` · `discount.php` | подвійні ціни ₴/€ за курсом, персональні знижки клієнтів |
| `i18n.php` | власний легкий UA/RU-перекладач (~470 фраз) без важких плагінів |
| `account.php` · `manager.php` | кабінет клієнта та кабінет менеджера (REST `enko/v1/*`) |
| `telegram.php` · `guest-chat.php` | двосторонній чат сайт ↔ Telegram (Topics), окремо для гостей |
| `search.php` | серверний пошук з автодоповненням, синонімами UA↔RU |
| `catalog-sync.php` | синхронізація каталогу з Google Sheet (CSV) |
| `backup.php` | бекапи БД із відновленням, ротація, захищене сховище |
| `seo.php` · `visibility.php` | meta/OG/JSON-LD, керування індексацією |
| `security.php` · `page-cache.php` | харденінг і файловий кеш сторінок |

## ⚡ Інженерні результати

Заміряно на живому сайті до / після оптимізації:

| Показник | Було | Стало |
|---|---|---|
| Вага фото головної (перший захід) | ~50 МБ | **~1 МБ** |
| Відповідь сервера (TTFB) | 0.45–0.85 с | **0.06–0.07 с** |
| Найважче зображення | 9 МБ (PNG) | 216 КБ (WebP) |
| Повторний візит | перекачував усе | кеш 30 днів |

**Як досягнуто:**
- усі контентні зображення переведено у **WebP** із коректними габаритами й перенесено в медіатеку
  WordPress (стали керованими з адмінки, а не «зашитими» в тему);
- **файловий page-cache для анонімних відвідувачів** (`dropins/advanced-cache.php`) — готовий HTML
  віддається до завантаження WordPress; кеш враховує мову, обходить кошик/кабінети/POST і
  скидається автоматично при зміні контенту чи налаштувань;
- `preload` критичних зображень, `preconnect` до шрифтів, кеш статики 30 днів.

### Безпека

Проведено власний аудит (код + живі неруйнівні проби + браузерні тести) і закрито:
примусовий HTTPS, вимкнення XML-RPC, блокування енумерації користувачів, security-заголовки
(HSTS, X-Frame-Options, Referrer-Policy тощо), honeypot + rate-limit на всіх формах,
уніфікована відповідь логіну (щоб не розкривати, які email зареєстровані), заборона редактора
файлів в адмінці, приховання версій.

## 🔒 Що не входить у цю копію

Свідомо виключено, щоб репозиторій був безпечним для публічного доступу:

- будь-які **доступи, ключі, паролі, конфігурації конекторів** до сервера й адмінки;
- **звіти з аудиту безпеки** живого сайту та журнали деплою;
- **внутрішні документи й інструкції** замовника, комерційні дані (прайс);
- **персональні дані** співробітників — у контактах стоять демо-плейсхолдери;
- PDF-документи виробників і фотографії реальних об'єктів (права третіх сторін).

Секрети ніколи не зберігалися в коді: усі ключі (Telegram, SMTP) читаються з налаштувань
у базі даних, тому код публікується без модифікацій цієї частини.
